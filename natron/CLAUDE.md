# Natron — Claude notes

Natron is a **separate app** from Androtone (the rest of this repository). It is a clean-room
recreation of Caustic 3 for Android, built with JUCE 8.0.12. Do not share code, build files, or
docs with Androtone, and do not change anything outside `natron/` when working on Natron (the only
exception is its CI workflow, `.github/workflows/natron.yml`).

Read `docs/spec.md` (what we are recreating) and `docs/roadmap.md` (where we are) before
non-trivial changes. Clean-room rule: work from observed behaviour and the public manual only;
never decompile Caustic or copy its assets. Reference screenshots or graphics may be looked at for
the general style, but never added to the repository, traced, or reproduced: draw our own.

## Layout

- `CMakeLists.txt` — desktop build: `Natron` app and `NatronTests`. CPM fetches JUCE into
  `external/JUCE` (git-ignored; fixed path so the Android export can use it too).
- `Natron.jucer` — Projucer project, used only for the Android export.
- `Builds/Android/`, `JuceLibraryCode/` — generated by Projucer from `Natron.jucer`; do not edit.
- `source/core/` — the engine and document model. No GUI or audio-device code: it is compiled
  into both the app and the tests.
  - `Transport` — beat ↔ sample mapping; `Pattern` / `PatternBank` / `PatternPlayer` — patterns →
    MIDI; `Machine` + `Parameter` — instrument interface and parameters; `MachineRegistry` —
    create machines by type name; `machines/` — one class per machine (`SubtractiveSynth`, `AcidBass`,
    `DrumMachine`, `Sampler`, `PadSynth`, `Bytebeat` + `BytebeatProgram`, `Modular`, `Organ`, `Vocoder`,
    `FmSynth`, `Pluck`, `Supersaw`), `VoiceMachine` (base for juce::Synthesiser-based ones), and the
    `TestToneMachine` placeholder (kept for tests).
  - `Automation` — automation lanes (pattern and song); `SampleData` — samples (import, song
    embedding); `SwappableResource` — lock-free swap for data the audio thread reads; `Autosave` —
    save on suspend/quit, restore on launch; `LiveRecorder` — pairs recorded live notes into
    pattern notes; `TapTempo`.
  - `dsp/` — shared DSP (`Biquad`, `Oscillator`, `DrumKit`, `FastSine` — use it rather than `std::sin`
    in per-sample loops). `mixer/` — `ChannelStrip` (one per
    machine, created and freed with it) and `MasterBus` (send returns, volume, limiter).
    `effects/` — `Effect` interface + registry (`Effects.cpp`), and the 18 insert effects
    (`Effects.h`, `MoreEffects.h`).
  - `Arrangement` — song timeline rows and their editing operations; `PatternEditing` — note
    editing operations for the piano roll. Pure functions: put new editing logic here, with tests,
    not in the views.
  - `SongExport` — offline render (on a private engine), WAV writing, and MIDI export.
  - `Engine` — audio thread: rack, pattern switching, mixer. Edited only via `EngineCommand`s.
  - `Song` — the document; `SongFile` — save/load; `Session` — message-thread API that edits the
    Song and posts the matching commands, and keeps the undo history. **UI code talks to
    `Session`, never to `Engine`'s rack directly.**
- `source/app/` — the JUCE app shell and UI. The layout follows the original app's screens (see
  `docs/spec.md` §8): a transport bar along the bottom and one page above it — the rack, a single
  vertical scroll of one-view-tall screens (`RackScroll`: per machine a sound editor and a pattern
  editor, then FX 1-7 / 8-14, Mixer 1-7 / 8-14, Master and the song timeline, `SongView`, which the
  Song key jumps to) — or `SettingsView` (menu). Every screen must fit one landscape phone screen (~870x390 dp);
  check new UI at that size. Graphics are our own (`NatronLookAndFeel`, drawn in code): use its
  palette (`surface`, `raised`, `line`, `text`, `textDim`, `accent`) and helpers (`drawPanel`,
  `drawSection`, `drawKey`, `drawLed`, `drawIcon`, `IconButton`) rather than new colours.
  `MainComponent` (bottom bar, menu, pages, export, MIDI inputs, autosave, back button),
  `RackScroll` (screens, left scroll grip, settling on screens, drum play pads), `PatternEditorView`
  (pattern keys toolbar and roll), `FxRackView` (effect pedals per machine), `MixerView` (7 strips or
  the master), `ChannelStripView` (one machine's channel, on the mixer and beside its sound editor),
  `ParameterPanel` (sectioned controls; fit-to-box shrinks a whole machine onto one screen),
  `PanelLayouts` (which parameters go in which section), `TouchKnob` (long-press fine adjust),
  `MachineExtrasPanel` (samples, formulas), `AutomationEditor` (lanes), `Theme` (colours, touch
  sizes), `PatternClipboard` (copy/paste menu items). `RackView` is the older all-machines pad grid,
  kept for its single-machine mode.
- `tests/` — Catch2 tests. `TestHelpers.h`: offline renderers and `Rig` (engine + session +
  renderer) and `MachineRig` (one machine); `Analysis.h`: pitch, centroid, band energy, onset;
  `TestMachines.h`: `RecordingMachine` (logs the MIDI it receives) and `DataMachine` (machine data);
  `AllocationCounter`: replaces global new/delete to prove the audio path never touches the heap.
  `Benchmarks.cpp`: hidden `[.benchmark]` CPU measurements (run them in a Release build).

Fingerprint tests (`GoldenTests.cpp`, `tests/golden/*.txt`) store RMS and spectral centroid per
50 ms rather than audio, with tolerances. If you change how something sounds **on purpose**,
regenerate them with `NATRON_UPDATE_GOLDEN=1 <build>/NatronTests_artefacts/<Config>/NatronTests "[golden]"`
and say so in the commit. An unexpected golden failure is a regression.

## Build and test (desktop)

```
cmake -S natron -B natron/build
cmake --build natron/build --target NatronTests
ctest --test-dir natron/build --output-on-failure
cmake --build natron/build --target Natron
```

Run the tests before every push; CI runs them on Linux.

## Build (Android)

Configure the desktop CMake once (so `external/JUCE` exists), then open `natron/Builds/Android` in
Android Studio or run `./gradlew assembleDebug` there.

## Adding files

- Add to `CMakeLists.txt` (`NATRON_CORE_SOURCES` for engine code, `Natron` target for app code, `NatronTests`
  for tests).
- Sync `Natron.jucer` with the source tree (`python3 natron/scripts/sync-jucer.py`), then regenerate
  the Android project: `Projucer --resave natron/Natron.jucer`.

## Conventions

- Engine code is real-time code: no allocation, freeing, locks, or I/O in `Engine::process` and
  below. Anything the audio thread replaces goes to the garbage queue. The "never touches the
  heap" test in `EngineTests.cpp` enforces this — extend its edit stream when adding commands.
- New machines: give them sections in `PanelLayouts.h` (parameters no rule names land in "More").
- New machines: subclass `Machine`, declare parameters in the constructor (set `interval` for
  discrete choices; 0/1 + interval 1 shows as a toggle), register the type in `MachineRegistry.cpp`.
  Parameter ids are saved in song files: never rename one. Do control-rate work on the voice's
  own sample counter, not per block, so output doesn't depend on block size (a test checks).
- Machine-specific data (samples, formulas, tables) goes through `Machine::getData/setData`; anything
  the audio thread reads from it is swapped with a `SwappableResource` (never freed on the audio thread).
- Undo: new `Session` edits must go through `edit(key, ...)` (see Session.cpp) so they are undoable,
  and `Session::restore` must apply the new state; the "Undoing everything restores the song
  exactly" test in `UndoTests.cpp` checks this — extend its edit list. Editor presses that edit
  continuously wrap themselves in `beginGesture` / `endGesture`.
- Song format changes: bump `SongFile::currentVersion` and upgrade older versions in
  `fromValueTree` (see the version notes in `SongFile.h`), with a test.
- Live MIDI (`Engine::pushLiveMidi`) is the only engine entry point safe from any thread; everything
  else goes through Session on the message thread.
- Catch2 treats commas in a test-name filter as "or": keep commas out of test names.
- Engine loops over sample ranges must always make progress: a segment end clamped to the current
  position must be followed by a jump or a return (see `Engine::generateMidi`).
- Musical time is in beats (double); sample positions are `int64_t` from `Transport`.
- New behaviour comes with an offline test that fails without it.
