# Claude project notes

## Project shape

Cliptone is a JUCE 8.0.12 audio plugin (synth): a Live-style clip-launching DAW, built as an original
recreation from public documentation (see `docs/rea/`). It lives on its own branch
(`ccr-2f1e2138-49ckmf`) and grew out of the Androtone codebase; it is a separate product. The project is described in `cliptone.jucer`
(Projucer), and there are two independent build paths:

- A hand-maintained CMake build at `Builds/desktop/CMakeLists.txt` for the desktop targets. CPM
  fetches JUCE at configure time into that build tree — no vendored sources.
- A Projucer-exported Android Studio / Gradle project under `Builds/android/` for the Android
  Standalone target.

Targets:

- VST3 — desktop hosts (Windows / macOS / Linux)
- Standalone — desktop
- Standalone — Android (Gradle + NDK; `Builds/android/app/CMakeLists.txt` is Projucer-generated)

## Layout

- `cliptone.jucer` — Projucer project: groups, modules, and the Android export config
- `JuceLibraryCode/` — Projucer-generated module shims + `JuceHeader.h` (do not edit)
- `Builds/desktop/CMakeLists.txt` — desktop build (CPM bootstrap, JUCE fetch, `juce_add_plugin`)
- `Builds/desktop/cmake-build-*-visual-studio/` — CLion-style build trees (also where CPM lands JUCE)
- `Builds/android/` — Projucer-exported Gradle project (regenerated by re-saving the `.jucer`)
- `source/` — plugin C++
  - `PluginProcessor.{h,cpp}`, `PluginEditor.{h,cpp}`
  - `Sequencer/` — clips (`ClipData.h`, `Clip.h`), tracks, `StepSequencer.h`, arrangement,
    recording (`Recorder.h`)
  - `Mixer/` — mixer and arrangement automation playback
  - `Project/` — demo presets and set (de)serialisation (`SetSerializer.h`)
  - `Ui/` — editor tabs (Session, Arrange, Clip, Device, Mixer, Settings, Projects)
  - `Engine/` — audio engine
    - `SoundSources/` — instruments (`AndroSynth.h`, `DrumKit.h`, sampler) and the metronome
    - `Processors/` — audio processors / effects that consume and produce audio
- `tests/` — headless tests; configure with `-DCLIPTONE_BUILD_TESTS=ON`, run `CliptoneTests`
- `scripts/` — helper scripts (e.g. `build-projucer.ps1` builds Projucer itself from the JUCE
  that CPM fetched into the desktop build tree)
- `docs/` — product requirements, design notes, and any Claude design files. `docs/rea/` holds the
  behaviour checklist (each item tied to evidence and a test) and the design-decision ledger. **Read everything in
  `docs/` before making non-trivial changes — it is the canonical source of intent for this
  project.**

## CI

`.github/workflows/build.yml` builds the Windows x64 Release standalone on pushes to this branch,
runs `CliptoneTests`, and uploads `Cliptone.exe` as the `cliptone-windows-x64` artifact. The VST3
is not built in CI.

## Build (desktop)

```
cmake -S Builds/desktop -B Builds/desktop/cmake-build-release-visual-studio
cmake --build Builds/desktop/cmake-build-release-visual-studio --config Release
```

CLion users can just open `Builds/desktop/CMakeLists.txt`.

VST3 lands in `Builds/desktop/cmake-build-release-visual-studio/Cliptone_artefacts/Release/VST3/`;
the standalone executable in `…/Cliptone_artefacts/Release/Standalone/`.

## Build (Android)

Open `Builds/android/` in Android Studio, or run `Builds/android/gradlew assembleRelease`. The
Gradle project and `Builds/android/app/CMakeLists.txt` are generated by Projucer — re-save
`cliptone.jucer` after changing modules, exporter settings, or the file list.

Note: the Projucer-generated Android CMake currently references JUCE sources via hard-coded paths
inside `Builds/desktop/cmake-build-debug-visual-studio/_deps/juce-src/`. The desktop CMake must
have been configured at least once so CPM has populated that path; re-save the `.jucer` if the
absolute path doesn't match this checkout's location.

## Keeping the project in sync

The desktop CMake is hand-maintained, not exported by Projucer. When adding files under `source/`:

- Add them to `cliptone.jucer` (so the Android export picks them up after a re-save).
- Add them to `target_sources(Cliptone …)` in `Builds/desktop/CMakeLists.txt`.

Plugin identity (synth flag, company, plugin/manufacturer codes, bundle ID) is currently set in
the desktop CMake; the Projucer-side identity defaults have not been aligned, so the Android
export will not match the desktop plugin metadata until that's fixed in the `.jucer`.

## Threading rules

The audio thread never allocates, frees or locks for long. Clip and arrangement content are
immutable snapshots (`ClipData::Ptr`, `ArrangementData::Ptr`). Editors copy, modify and
`sanitise()`/`render()` a fresh snapshot, then swap it in. Replaced snapshots go to the
`ReleasePool` and are freed on the message thread. Small settings are atomics. Recording and
arrangement logging send events from the audio thread through lock-free FIFOs (`RecordEvents.h`).
